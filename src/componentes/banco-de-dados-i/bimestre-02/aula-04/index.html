Teoria & Conceitos

1. O Modelo Lógico de Dados

O Modelo Lógico é a segunda etapa do projeto de banco de dados, situada entre o modelo conceitual (independente de tecnologia) e o modelo físico (específico de um SGBD).

  • Objetivo: Descrever as estruturas que estarão no banco de dados de acordo com a abordagem tecnológica escolhida (neste caso, a Relacional), mas sem considerar características físicas como índices ou caminhos de acesso.
  • Transição: Enquanto no modelo conceitual falamos em "Entidades" e "Relacionamentos", no modelo lógico passamos a falar em Tabelas (Relações), Atributos (Colunas) e Tuplas (Linhas).

2. O Conceito de Tabela (Relação)

A abordagem relacional, criada por Edgar F. Codd em 1970, baseia-se no princípio de que as informações podem ser representadas uniformemente como tabelas bidimensionais.

A. Premissas de uma Tabela Relacional:

Para que uma estrutura seja considerada uma tabela (relação) válida na teoria relacional, ela deve seguir certas regras:

  • Nome Único: Cada tabela deve ter um nome distinto das demais no banco de dados.
  • Valores Atômicos: Cada atributo (coluna) deve conter valores indivisíveis. Não são permitidos "subgrupos" ou múltiplos valores em uma única célula (multivaloração).
  • Unicidade das Linhas: Não podem existir duas linhas (tuplas) idênticas em uma mesma tabela.
  • Ordem Irrelevante: A ordem em que as linhas ou colunas aparecem é tecnicamente irrelevante para o funcionamento lógico.
  • Nomes de Colunas: Cada coluna possui um nome que identifica o significado de seu conteúdo.

B. Representação Gráfica (Estrutura Lógica)

No modelo lógico, representamos a tabela e seus atributos, indicando qual coluna atua como identificador único.

classDiagram
    class CLIENTE {
        +int Cod_Cliente (PK)
        +string Nome
        +int Idade
        +string CPF
        +string Cidade

3. O Conceito de Domínio

O Domínio é o fundamento da integridade dos dados no nível lógico. Ele representa o conjunto de valores atômicos admissíveis para uma determinada coluna.

  • Finalidade: Estabelecer restrições para garantir que os valores inseridos façam sentido. Por exemplo, um domínio de "Idade" pode ser restrito a números inteiros entre 0 e 120.
  • Associação com Tipos: A cada domínio está associado um tipo de dado (integer, float, char, date) ou um formato específico.

Exemplos Práticos de Domínios:

  • Sexo: Lista enumerada {'M', 'F'}.
  • CPF: Conjunto de 11 dígitos numéricos.
  • Salário: Valores numéricos decimais positivos.

4. Demonstração Prática: Esquema vs. Instância

A distinção entre a definição da tabela e os dados reais é crucial:

  • Esquema (Intenção): É a definição da estrutura. Exemplo: ESTUDANTE (Nome, NSS, Telefone, MPA).
  • Instância (Extensão): É o conjunto de dados (tuplas) presentes na tabela em um determinado momento.

Exemplo de Tabela "FUNCIONÁRIO" (Instância):

NumReg (PK) NomeFunc DtAdmissão Sexo CdDepto (FK)
101 Luis Sampaio 10/08/2003 M D5
104 Carlos Pereira 02/03/2004 M D6
195 Marta Silveira 05/01/2002 F D5

Nota Teórica: Na tabela acima, as colunas representam os atributos, e cada linha completa representa uma tupla (um fato sobre um funcionário específico).

Dicas & Lembretes

1. Estrutura e Premissas das Tabelas (Relações)

  • Terminologia Técnica: Lembre-se de que, formalmente, uma tabela é chamada de relação, uma linha é uma tupla e uma coluna é um atributo.
  • Unicidade: Não podem existir duas linhas idênticas em uma mesma tabela. Cada fato registrado deve ser distinguível dos demais através de sua Chave Primária (PK).
  • Ordem Irrelevante: Tecnicamente, a ordem em que as linhas ou colunas aparecem no banco de dados não afeta o resultado lógico das consultas.
  • Nomenclatura: Cada tabela deve possuir um nome exclusivo dentro do banco de dados para evitar ambiguidades.

2. Domínios e Atributos

  • Valores Atômicos: Cada célula da tabela deve conter apenas um valor indivisível. Não é permitido o uso de subgrupos ou listas de valores (multivaloração) dentro de um único atributo.
  • O Papel do Domínio: O domínio define o conjunto de valores "legais" para uma coluna (ex: um domínio de "Nota" entre 0 e 10). Ele impede que dados sem sentido sejam inseridos e garante que as comparações em consultas sejam válidas.
  • Tipos de Dados: A cada domínio está associado um tipo físico (integer, char, date, etc.), mas o domínio é um conceito mais restritivo que o simples tipo.

3. Esquema vs. Instância

  • Esquema (Intenção): É a "fotocópia" ou o plano do banco de dados, definindo as tabelas e suas regras. Ele raramente muda.
  • Instância (Extensão): São os dados reais presentes no banco em um momento específico. A instância muda constantemente conforme registros são inseridos ou deletados.

4. Integridade de Entidade (Chave Primária)

  • Regra de Ouro: Os atributos que compõem a Chave Primária nunca podem aceitar valores nulos (NOT NULL).
  • Identificação Unívoca: Se a PK for nula, o registro torna-se "desconhecido" e não distinguível, o que violaria a integridade da tabela.
  • Chaves Candidatas: Uma tabela pode ter várias colunas com valores únicos (chaves candidatas), mas apenas uma é escolhida para ser a Chave Primária oficial.

5. Boas Práticas de Modelagem Lógica

  • Evite Nulos Excessivos: Projetar tabelas onde a maioria das tuplas possui valores nulos em certas colunas pode indicar um erro de modelagem (talvez esses dados devessem estar em uma tabela separada).
  • Semântica Clara: Cada tabela deve representar apenas um assunto ou tipo de entidade. Misturar atributos de entidades diferentes (ex: colocar dados do departamento na tabela de funcionários de forma repetitiva) gera redundâncias e anomalias de atualização.
  • Independência de Dados: O modelo lógico deve ser construído pensando na tecnologia escolhida (ex: Relacional), mas ainda sem se preocupar com detalhes físicos de hardware ou armazenamento, garantindo maior flexibilidade.
