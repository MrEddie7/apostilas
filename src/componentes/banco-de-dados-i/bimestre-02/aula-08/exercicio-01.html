1. Enunciado e Contexto de Negócio

Uma Startup de tecnologia financeira (Fintech) contratou você para realizar a modelagem do banco de dados de um novo produto: o MyPocket, um sistema de controle e auditoria de finanças domésticas.

Diferente de planilhas comuns, o grande diferencial competitivo do MyPocket no mercado é a sua arquitetura de segurança de dados, projetada para atuar na prevenção do endividamento e garantir a integridade absoluta do histórico financeiro do usuário.

Para que o sistema funcione com segurança, o banco de dados deve ser modelado seguindo Regras de Negócio (RN) estritas:

  • RN01 - Controle de Endividamento: O saldo acumulado do usuário nunca poderá ficar negativo no sistema. Toda despesa que ultrapasse o saldo atual deve ser bloqueada antes de ser registrada.
  • RN02 - Classificação Rígida de Fluxo: Não existem movimentações genéricas. Toda e qualquer transação deve ser categorizada estritamente como uma Receita (ganho/entrada) ou uma Despesa (gasto/saída).
  • RN03 - Histórico Inalterável (Imutabilidade): Por questões de auditoria financeira, uma transação gravada no banco nunca poderá ser alterada (com o comando UPDATE) ou apagada (com o comando DELETE). Se um lançamento foi feito com valor errado, o usuário é obrigado a lançar uma nova transação de estorno (uma receita para anular uma despesa errada, ou vice-versa).

2. Preparação e Premissas Técnicas

  • Ferramentas: Utilize um software CASE de modelagem de dados (sugestão: brModelo, draw.io ou equivalente).
  • Restrições de Padrão de Projeto (Naming Conventions):
    • Nomes de tabelas devem ser definidos obrigatoriamente no plural (ex: usuarios).
    • Todas as chaves primárias devem adotar estritamente o nome id.
    • Campos compostos devem utilizar o padrão snake_case (letras minúsculas separadas por underline, ex: data_transacao).

3. O Desafio (Atividades Práticas)

Parte 1: Modelo Conceitual (MER)

Com base no contexto do sistema, elabore o Diagrama Entidade-Relacionamento (DER) abstrato atendendo aos seguintes critérios teóricos:

  • Mapeie as entidades fortes primárias: Usuario (titular do sistema), Carteira (onde o saldo é guardado e protegido) e Transacao.
  • Defina as cardinalidades máximas e mínimas das associações. Atente-se à regra: Um usuário possui apenas uma carteira ativa no sistema, e uma carteira pertence a apenas um usuário.
  • Aplique o conceito de Abstração Avançada de Generalização/Especialização na entidade Transacao. O modelo deve demonstrar visualmente que Transacao é a superclasse que se especializa nas subclasses Receita e Despesa. Classifique no diagrama se essa especialização é Total (t) ou Parcial (p), Exclusiva (e) ou Compartilhada (c).

Parte 2: Modelo Lógico (Esquema Relacional)

Aplique as regras de derivação para transformar seu modelo conceitual em um esquema lógico de tabelas textuais.

  • Escreva a estrutura de dicionário/linhas das tabelas geradas.
  • Demonstre como a relação 1:1 entre Usuário e Carteira foi resolvida através do posicionamento estratégico da Chave Estrangeira (FK).
  • Mapeamento de Herança: Justifique a estratégia adotada para mapear a herança de Transacao para a estrutura relacional (tabela única para a superclasse com campo discriminador, ou tabelas separadas para as subclasses).

Parte 3: Dicionário de Dados e Restrições de Integridade

Documente a estrutura exata das tabelas carteiras e transacoes, montando uma tabela descritiva contendo:

  • Nome do Campo.
  • Tipo de Dado específico (Justifique a escolha do tipo de dado ideal para os campos de valores financeiros, visando impedir problemas de arredondamento).
  • Restrições de Integridade (Identifique quais campos devem receber travas como NOT NULL, UNIQUE, ou cláusulas CHECK).

4. Orientações Finais e Critérios de Homologação

Para que o seu projeto seja aprovado pela governança de dados da Fintech, os seguintes pontos serão testados no seu modelo:

  • Teste de Unicidade: O banco impede fisicamente que o mesmo usuário tenha duas carteiras registradas?
  • Teste de Imutabilidade: As restrições e configurações das Chaves Estrangeiras (como ON DELETE e ON UPDATE) foram configuradas de modo a impedir que a exclusão de um usuário apague o histórico de transações que passaram por auditoria?
  • Precisão Numérica: Foi evitado o uso de tipos de dados de ponto flutuante imprecisos (como FLOAT ou DOUBLE) para o dinheiro?
