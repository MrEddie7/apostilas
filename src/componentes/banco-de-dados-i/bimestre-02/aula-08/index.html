1. Introdução: O Valor da Engenharia de Dados

No mercado de tecnologia e sistemas corporativos, os dados são o ativo mais valioso de uma organização. Quando falamos do setor de tecnologia financeira (Fintechs), a precisão, a segurança e a consistência desses dados tornam-se uma questão de sobrevivência institucional. Um erro matemático de um centavo ou a perda acidental de um histórico de transações pode arruinar a reputação de um software e quebrar uma empresa.

Muitos desenvolvedores iniciantes cometem o erro de começar a escrever códigos de programação antes de desenhar a estrutura onde esses dados serão armazenados. O resultado disso são sistemas lentos, com dados duplicados e falhas graves de segurança.

O banco de dados é a "Memória" de um software. Se essa memória for mal estruturada, toda a aplicação será frágil. Neste projeto prático, você atuará como Engenheiro e Arquiteto de Dados para planejar, modelar e proteger a infraestrutura do MyPocket, um sistema de gestão financeira doméstica e auditoria de fluxo de caixa.

2. O Minimundo e os Requisitos de Negócio (RN)

O primeiro passo de qualquer modelagem é compreender o "Minimundo" (o recorte da realidade que o software vai controlar) e as Regras de Negócio impostas pelo cliente.

O Cenário (Minimundo):

O MyPocket permite que usuários gerenciem suas finanças pessoais. O sistema deve identificar cada usuário por um código exclusivo, guardando seu nome e e-mail. Para proteger o patrimônio, cada usuário possui uma única Carteira onde fica registrado seu saldo disponível. Dentro dessa carteira, ocorrem diversas movimentações de dinheiro, chamadas de Transações. Cada transação possui um identificador único, uma descrição textual, a data em que ocorreu e o valor financeiro envolvido.

Para garantir que o sistema seja robusto e confiável, a diretoria da Fintech estabeleceu três Regras de Negócio inegociáveis que devem ser garantidas diretamente pela arquitetura do banco de dados:

  • RN01 - Controle Preventivo de Endividamento: O saldo acumulado da carteira do usuário nunca poderá ficar negativo no sistema. Nenhuma transação de saída de dinheiro pode ser processada se o valor for maior do que o saldo atual líquido disponível.
  • RN02 - Classificação Rígida de Fluxo: Não existem movimentações genéricas. Toda e qualquer transação inserida na plataforma deve ser categorizada estritamente como uma Receita (ganho/entrada) ou uma Despesa (gasto/saída), permitindo a geração de relatórios analíticos limpos.
  • RN03 - Histórico Inalterável (Imutabilidade): Por motivos de auditoria e consistência fiscal, uma transação gravada no banco de dados nunca poderá ser alterada ou apagada. Se um lançamento foi realizado com o valor incorreto, o usuário é proibido de editar o registro; ele deverá obrigatoriamente realizar uma nova transação de estorno (uma receita para anular uma despesa errada, ou vice-versa), mantendo a linha do tempo intacta.

3. O Desafio Prático: Etapas de Execução

Sua missão nesta atividade está dividida em três fases progressivas, simulando o fluxo de trabalho de um profissional de engenharia de dados no mercado de trabalho.

Parte 1: Modelo Conceitual (Diagrama Entidade-Relacionamento)

Utilizando uma ferramenta CASE (como brModelo, draw.io ou equivalente), crie o Modelo Entidade-Relacionamento (MER) abstrato do sistema seguindo as diretrizes teóricas:

  • Mapeamento de Entidades e Atributos: Identifique e desenhe as entidades fortes primárias (Usuario, Carteira e Transacao). Adicione a cada uma delas seus respectivos atributos descritivos, marcando de forma explícita quais serão os atributos identificadores (Chaves Primárias).
  • Definição de Cardinalidades: Estabeleça as restrições de conectividade máxima e mínima para os relacionamentos. Lembre-se da regra do negócio: Um usuário possui uma, e apenas uma, carteira ativa; e uma carteira pertence exclusivamente a um único usuário.
  • Abstração Avançada (Herança no Banco de Dados): Aplique o conceito de Generalização/Especialização para a entidade Transacao. O diagrama deve demonstrar visualmente que Transacao funciona como uma superclasse (entidade genérica) que se especializa nas subclasses Receita e Despesa. Classifique no triângulo de ligação se essa especialização é Total (t) ou Parcial (p), e se é Exclusiva (e) ou Compartilhada (c), baseando-se na RN02.

Parte 2: Modelo Lógico (Esquema Relacional de Tabelas)

Realize a transposição do seu modelo abstrato (Parte 1) para um modelo lógico-relacional, aplicando estritamente as regras de derivação de diagramas para tabelas:

  • Padrão de Nomenclatura Corporativo: Escreva a estrutura textual das tabelas geradas adotando o padrão de nomes obrigatoriamente no plural (ex: usuarios, carteiras, transacoes).
  • Padronização de Chaves: Todas as chaves primárias do sistema devem adotar obrigatoriamente a nomenclatura simplificada id. Campos compostos devem adotar o padrão snake_case (letras minúsculas separadas por sublinhado, ex: data_transacao).
  • Resolução de Relacionamentos: Demonstre em qual tabela ficará posicionada a Chave Estrangeira (FK) para resolver o relacionamento 1:1 (Usuário/Carteira) de forma que o banco impeça um usuário de criar uma segunda carteira.
  • Estratégia de Mapeamento de Herança: Defina e justifique textualmente qual estratégia de mapeamento de subclasses você escolheu para o banco de dados (Tabela Única para a Superclasse contendo um campo descritor/tipo; ou Tabelas Separadas para cada subclasse).

Parte 3: Dicionário de Dados e Restrições de Integridade

A consistência dos dados depende de regras rígidas sobre o que cada campo pode aceitar. Crie o Dicionário de Dados técnico detalhando a estrutura das tabelas carteiras e transacoes. Monte uma tabela para cada uma contendo as seguintes colunas de documentação:

  • Nome do Campo: O nome físico da coluna na tabela.
  • Tipo de Dado: O tipo exato de dado do banco de dados (Atenção: Justifique por que tipos de ponto flutuante imprecisos como FLOAT ou DOUBLE devem ser proibidos para armazenar dinheiro e qual tipo deve ser usado em seu lugar).
  • Restrições (Constraints): Defina quais campos não aceitam valores vazios (NOT NULL), quais exigem valores únicos (UNIQUE) e quais devem possuir validações de valores permitidos (Cláusulas CHECK ou ENUM).
  • Descrição: A finalidade de negócio daquele campo.

4. Orientações Finais e Critérios de Homologação

Para que o seu projeto de modelagem seja aprovado pela governança de dados da Fintech, a estrutura apresentada passará por quatro testes de fogo lógicos:

  • O Teste da Unicidade Financeira: Olhando para o seu modelo lógico, o banco de dados rejeitará fisicamente se um script tentar associar uma nova carteira a um usuário que já possui uma cadastrada?
  • O Teste da Imutabilidade Histórica: Se um usuário for descadastrado do sistema, as configurações das suas Chaves Estrangeiras (ON DELETE e ON UPDATE) foram configuradas para proibir a exclusão em cascata (RESTRICT / NO ACTION), impedindo que o histórico auditável de transações suma do mapa?
  • O Teste da Precisão Centesimal: Se o sistema rodar um cálculo de soma acumulada de um milhão de transações, o tipo de dado escolhido para as colunas de valor garante que nenhum centavo se perca por arredondamento computacional?
  • O Teste da Blindagem de Fluxo: O banco de dados impede que uma transação nasça sem dizer explicitamente se ela é uma Entrada ou uma Saída de dinheiro?

A engenharia de dados de um sistema de grande porte começa no desenho do seu alicerce. Ao concluir estas três etapas, você terá desenhado uma estrutura de dados robusta, profissional, performática e completamente preparada para ser implementada em qualquer Sistema Gerenciador de Banco de Dados (SGBD) do mercado.
