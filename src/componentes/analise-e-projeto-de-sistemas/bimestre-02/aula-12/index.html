Teoria & Conceitos

1. Visão Geral e Propósito

O Diagrama de Caso de Uso é um diagrama comportamental da UML que captura os requisitos funcionais de um sistema sob uma perspectiva externa e independente de implementação. Ele não descreve mecanismos internos ("como"), mas sim o que o sistema deve fazer do ponto de vista de seus usuários externos.

  • Objetivo: Delimitar o escopo (fronteiras) do sistema e identificar as interações fundamentais entre ele e seu ambiente.
  • Foco no Usuário: Cada caso de uso representa um objetivo do usuário (ou meta) que agrega valor ao negócio.

2. Elementos Gráficos Fundamentais

O diagrama utiliza uma notação simples para facilitar a comunicação entre técnicos e clientes.

A. Atores (Actors)

Representam os papéis desempenhados por pessoas, outros sistemas de software ou dispositivos de hardware que interagem com o sistema.

  • Notação: Geralmente representados por um "boneco palito" (stick figure) com o nome do papel abaixo. Alternativamente, podem ser exibidos como retângulos com o estereótipo «actor».
  • Conceito Chave: Um ator é uma idealização de um papel, não uma pessoa específica; um indivíduo real pode atuar como vários atores em momentos distintos.
  • Exemplo Prático: Em um sistema acadêmico, o "Aluno" e o "Professor" são atores; um sistema de cobrança legado também pode ser um ator se receber dados do novo sistema.

B. Casos de Uso (Use Cases)

Representam uma unidade coerente de funcionalidade que o sistema executa.

  • Notação: Uma elipse contendo um nome descritivo, preferencialmente um verbo de ação (Ex: "Fazer Pedido", "Sacar Dinheiro").
  • Escopo: Um caso de uso é considerado completo quando o objetivo do usuário é atingido ou um erro ocorre.

C. Limite do Sistema (Subject/System Boundary) (5)

Um retângulo que envolve os casos de uso, deixando os atores do lado de fora.

  • Propósito: Define claramente o que está dentro da responsabilidade do software que será desenvolvido e o que é externo a ele.
  • Exemplo Prático: Ao modelar um Caixa Eletrônico (ATM), as funções como "Sacar Dinheiro" estão dentro do limite, enquanto o "Cliente" e o "Sistema Bancário Central" estão fora.

3. Relacionamentos no Diagrama

Os elementos são conectados para mostrar como a funcionalidade é organizada.

  • Associação (1): Uma linha sólida entre um ator e um caso de uso indicando que eles se comunicam. Pode conter setas direcionais para mostrar quem inicia a comunicação.
  • Inclusão («include») (2): Uma seta tracejada do caso de uso base para o incluído. Indica que o comportamento do segundo é obrigatório para o primeiro.
    • Exemplo: O caso de uso "Realizar Pedido" sempre inclui "Validar Cliente".
  • Extensão («extend») (3): Uma seta tracejada do caso de uso que estende para o caso de uso base. Indica um comportamento opcional ou excepcional que ocorre sob condições específicas em "pontos de extensão".
    • Exemplo: "Emitir Recibo" pode estender "Fazer Compra" apenas se o cliente solicitar.
  • Generalização (4): Representada por uma linha com um triângulo vazio apontando para o elemento mais geral.
    • Entre Atores: "Novo Cliente" pode ser uma especialização de "Cliente".
    • Entre Casos de Uso: "Pagar com Cartão" e "Pagar com Boleto" podem ser especializações de "Realizar Pagamento".

4. Exemplos Práticos de Modelagem Gráfica

Exemplo 1: Sistema de Bilheteria de Teatro

Neste cenário, o Assunto (Subject) é o "Box Office".

  • Atores: "Clerk" (atendente), "Kiosk" (autoatendimento) e "Supervisor".
  • Casos de Uso Principais: "Buy Tickets" e "Survey Sales".
  • Relacionamentos: Ambos "Clerk" e "Kiosk" iniciam "Buy Tickets". O caso de uso "Buy Tickets" possui um relacionamento de «include» com "Make Charges" (sistema de cartão), pois o pagamento é essencial para a compra.

Exemplo 2: Sistema de Controle Acadêmico (UAB)

Este exemplo foca nas permissões e funcionalidades macro.

  • Atores: "Aluno", "Professor", "Coordenador" e sistemas legados como "Sistema de RH".
  • Casos de Uso:
    • O Aluno interage com "Realizar Inscrição" e "Visualizar Notas".
    • O Professor interage com "Lançar Avaliações".
    • O Sistema de Faturamento (Ator Sistema) recebe informações de "Realizar Inscrição" via uma associação.

5. Processo de Construção do Diagrama Gráfico

Para garantir a completude do diagrama, o analista deve seguir estes passos:

  1. Definir a Fronteira: Desenhar o retângulo do sistema e nomeá-lo.
  2. Identificar os Atores: Listar todos os usuários e sistemas externos que precisam de algo do sistema.
  3. Identificar os Casos de Uso: Identificar os grandes objetivos que cada ator deseja alcançar (evitar excesso de detalhes, mantendo entre 6 a 8 casos de uso por diagrama).
  4. Adicionar Associações: Ligar os atores às suas funcionalidades.
  5. Refinar com Inclusões e Extensões: Procurar comportamentos comuns (reuso) ou opcionais para organizar o diagrama.

Dica Lembrete

  • O diagrama de caso de uso não deve tentar mostrar a ordem cronológica das tarefas; para isso, utilizam-se diagramas de interação como o de Sequência.
