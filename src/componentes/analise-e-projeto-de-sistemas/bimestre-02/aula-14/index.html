Teoria & Conceitos

1. Introdução aos Casos de Uso

Na Engenharia de Software contemporânea, fundamentada pela perspectiva pragmática de Martin Fowler, um Caso de Uso é definido como um conjunto de cenários amarrados por um objetivo comum de um usuário. A maior falha de um analista iniciante é focar excessivamente na representação gráfica (o diagrama). É imperativo notar que o valor real da técnica reside no texto descritivo. O diagrama serve apenas como um sumário; a inteligência do requisito está na narrativa detalhada da interação.

2. Entidades Fundamentais: Atores e Cenários

Para uma especificação tecnicamente precisa, devemos distinguir claramente estas duas entidades:

  • Ator: Representa um papel desempenhado por um usuário em relação ao sistema, e não uma pessoa específica. Atores podem ser seres humanos ou sistemas externos para os quais o software fornece um serviço.
  • Cenário: É uma sequência de passos de interação. Um caso de uso agrupa vários cenários: um caminho ideal de sucesso e diversos caminhos de exceção ou variação.

3. Níveis de Detalhamento e Objetivos

Fowler categoriza os casos de uso em diferentes níveis de abstração. O foco do analista deve estar majoritariamente no "Nível do Mar", que representa a entrega de valor real.

Nível Objetivo Valor para o Ator
Pássaro (Bird-level) Visão de alto nível e processos de negócio amplos. Contextualiza o valor organizacional.
Mar (Sea-level) Nível Primário. Interação direta Ator-Sistema. Entrega um objetivo discreto (5 a 30 min).
Peixe (Fish-level) Subfunções ou passos incluídos. Não possui valor isolado; suporta o nível do mar.

Diferenciamos ainda o Caso de Uso de Negócio (como a organização responde a um evento externo) do Caso de Uso de Sistema (como o software responde especificamente).

4. Estrutura de um Caso de Uso "Fully Dressed" (Completo)

Uma especificação madura exige uma estrutura formal para evitar ambiguidades e falhas de implementação.

  • Identificação: Nome do objetivo (ex: Compra de um Produto) e indicação do Nível (ex: Nível do Mar).
  • Atores:
    • Ator Principal: Aquele cujo objetivo o caso de uso tenta satisfazer (o iniciador).
    • Ator Secundário: Sistemas externos que o software precisa consultar (ex: Serviço de Crédito).
  • Gatilho (Trigger): O evento exato que dispara a execução da lógica.
  • Pré-condições: O que deve ser verdade antes do início. Como engenheiros, usamos pré-condições para permitir que o programador evite verificações redundantes no código, assumindo que o estado anterior já foi validado.
  • Pós-condições/Garantias:
    • Garantias de Sucesso: O estado do sistema após o objetivo ser atingido.
    • Garantias Mínimas: O que o sistema assegura em qualquer cenário, mesmo na falha (ex: auditoria de log ou rollback). Isso protege os interesses dos stakeholders independentemente do sucesso do ator.

5. Dinâmica dos Fluxos: O Cenário Principal e Extensões

A narrativa textual deve seguir a regra de ouro: cada passo deve ser uma declaração simples de interação com um ator visível e uma intenção clara.

  • Cenário Principal de Sucesso (CPS): É o "caminho feliz". Uma lista numerada de passos onde tudo ocorre perfeitamente.
  • Extensões: Tratam as variações e falhas. Nomeamos a condição detectada em um passo do CPS (ex: "6a. Autorização negada") e detalhamos o fluxo alternativo.

6. Relacionamentos Aplicados ao Texto (Include e Extend)

Ao redigir, o analista deve otimizar o texto sem torná-lo uma "teia" ilegível de diagramas. Dicas de escrita:

  • Representação do <<include>>: Utilize o sublinhado para indicar que um passo é, na verdade, um chamado a outro caso de uso (ex: Validar Usuário). Isso evita repetição de lógica complexa.
  • A Crítica ao <<extend>>: Martin Fowler é contundente ao sugerir que você ignore o <<extend>>. Na prática, ele frequentemente leva à "decomposição funcional", complicando o entendimento. Prefira descrever as variações na seção de Extensões do texto.

7. Exemplo Prático: Compra de um Produto

Caso de Uso: Compra de um Produto
Nível: Nível do Mar

Cenário Principal de Sucesso:

  1. O cliente navega pelo catálogo e seleciona itens para comprar (inclui Adicionar à Cesta).
  2. O cliente vai para o caixa.
  3. O cliente preenche o formulário de remessa (endereço e opção de entrega imediata ou em 3 dias).
  4. O sistema apresenta a informação completa do faturamento, incluindo a remessa.
  5. O cliente preenche a informação do cartão de crédito.
  6. O sistema autoriza a compra.
  7. O sistema confirma imediatamente a venda.
  8. O sistema envia uma confirmação para o cliente por e-mail.

Extensões:

  • 3a. Cliente regular:
    1. O sistema mostra a informação atual de remessa, preço e cobrança.
    2. O cliente pode aceitar ou sobrescrever os padrões, retornando ao passo 6.
  • 6a. O sistema falha na autorização da compra:
    1. O cliente pode inserir novamente a informação do cartão ou cancelar a operação.

Aprofundando a Prática

Abaixo, veremos três exemplos práticos e progressivos baseados no contexto de um sistema acadêmico.

Exemplo 1: Nível Básico (Foco em fluxo linear)

CSU01: Fazer Login

  • Ator Principal: Usuário (Professor ou Aluno)
  • Breve Descrição: O usuário acessa o sistema informando suas credenciais para visualizar seu painel de controle (Dashboard).
  • Pré-condições: O usuário deve estar previamente cadastrado no sistema.

Fluxo Principal:

  1. O usuário acessa a página de autenticação.
  2. O sistema exibe os campos de usuário e senha.
  3. O usuário insere suas credenciais e clica em "Entrar".
  4. O sistema valida as credenciais no banco de dados.
  5. O sistema redireciona o usuário para o Dashboard.

Fluxo de Exceção (4a) - Credenciais Inválidas:

  1. O sistema identifica que o usuário ou a senha estão incorretos.
  2. O sistema exibe a mensagem "Acesso Negado".
  3. O caso de uso retorna ao passo 2 do Fluxo Principal.

Pós-condições: O usuário está autenticado e com a sessão ativa.

Exemplo 2: Nível Intermediário (Com inclusão de outro caso de uso)

CSU02: Postar Material de Aula

  • Ator Principal: Professor
  • Breve Descrição: Permite que o professor publique arquivos, links ou textos de apoio para uma disciplina específica.
  • Pré-condições: O professor deve estar autenticado (Inclui CSU01) e vinculado à disciplina.

Fluxo Principal:

  1. O professor seleciona a disciplina desejada no painel.
  2. O sistema exibe a tela da disciplina e a opção de "Postar Material".
  3. O professor preenche o título, a descrição e faz o upload do arquivo.
  4. O professor clica em "Publicar".
  5. O sistema salva o material, vincula-o à disciplina e envia uma notificação aos alunos matriculados.

Fluxo Alternativo (3a) - Material sem arquivo fixado:

  1. O professor opta por postar apenas um aviso em texto, sem anexar arquivos.
  2. O caso de uso prossegue a partir do passo 4 do Fluxo Principal.

Pós-condições: O material está disponível para os alunos daquela disciplina.

Exemplo 3: Nível Avançado (Com fluxos alternativos múltiplos)

CSU03: Entregar Tarefa

  • Ator Principal: Aluno
  • Breve Descrição: O aluno realiza o envio do arquivo correspondente a uma tarefa solicitada em uma disciplina.
  • Pré-condições: O aluno deve estar autenticado e matriculado na disciplina.

Fluxo Principal:

  1. O aluno acessa a área da disciplina e clica na tarefa pendente.
  2. O sistema exibe as instruções da tarefa e o prazo de entrega.
  3. O aluno faz o upload do arquivo da sua resolução.
  4. O aluno clica em "Enviar Tarefa".
  5. O sistema registra a data/hora do envio e exibe um recibo de sucesso.

Fluxo Alternativo (2a) - Tarefa Atrasada (Se o sistema permitir):

  1. O sistema identifica que a data atual é posterior ao prazo limite.
  2. O sistema exibe um aviso informando que a entrega será marcada como "Atrasada".
  3. O caso de uso prossegue para o passo 3, mas salva o status de atraso.

Fluxo de Exceção (3b) - Arquivo muito grande ou formato inválido:

  1. O sistema valida o arquivo e detecta que ele excede o limite (ex: 20MB) ou possui formato proibido (ex: .exe).
  2. O sistema exibe uma mensagem de erro ("Formato ou tamanho inválido").
  3. O caso de uso retorna ao passo 2.

Pós-condições: O arquivo da tarefa foi armazenado no sistema com as respectivas marcações de data e status.

Dicas de Validação e Boas Práticas

Utilize este checklist para revisar suas especificações antes da entrega técnica:

  • Independência de Interface (UI): O texto foca na intenção ("o cliente confirma") e não no mecanismo ("o cliente clica no botão azul").
  • Brevidade: O documento é curto o suficiente para ser lido em uma pausa para o café? Documentação exaustiva é documentação ignorada.
  • Projeto por Contrato: As asserções (Pré e Pós-condições) estão claras? Elas são a ponte entre o requisito e o desenvolvimento robusto (assertions no código).
  • Comunicação Verbal: O caso de uso serviu como base para uma conversa com o cliente ou foi apenas um "depósito de papel"?
  • Foco no Nível do Mar: A maioria dos casos de uso descreve tarefas de 5 a 30 minutos com valor direto para o ator?
