Projeto MyPocket

Nesta aula, consolidaremos os conhecimentos de Programação Orientada a Objetos (POO) com o desenvolvimento do Projeto MyPocket.

1. Requisitos de Negócio (RN)

As regras macro e objetivos que definem o valor do software para o cliente ou usuário final.

  • RN01 - Controle de Endividamento: O sistema deve atuar como uma ferramenta preventiva de saúde financeira. Portanto, o saldo acumulado do usuário nunca poderá ficar negativo, forçando a consciência sobre os limites de gastos.
  • RN02 - Classificação de Fluxo: Toda e qualquer movimentação financeira na plataforma deve ser categorizada estritamente como uma entrada (ganho) ou uma saída (gasto) para fins de relatórios analíticos limpos.
  • RN03 - Histórico Inalterável: Por questões de auditoria e consistência financeira doméstica, uma transação realizada não pode ser editada diretamente; se um lançamento foi feito errado, o usuário deve lançar uma transação de estorno (uma receita para anular uma despesa, ou vice-versa).

2. Requisitos Funcionais (RF)

O que o sistema deve fazer (as funcionalidades que os alunos programarão no front e back-end).

  • RF01 - Cadastro de Receitas: O sistema deve apresentar um formulário para entrada de valores positivos (Salário, Freelance, Pix recebido). O lançamento deve exigir valor, descrição e data.
  • RF02 - Cadastro de Despesas: O sistema deve apresentar um formulário para entrada de valores de débito (Aluguel, Mercado, Luz). O lançamento deve exigir valor, descrição e data.
  • RF03 - Exibição de Saldo Atual: O sistema deve calcular dinamicamente e exibir em destaque na tela o saldo líquido disponível na carteira do usuário.
  • RF04 - Extrato Consolidado (Histórico): O sistema deve listar todas as transações enviadas em ordem cronológica, exibindo de forma clara a descrição, a data, o valor e o tipo (Entrada/Saída).
  • RF05 - Diferenciação Visual por Tipo: O extrato deve aplicar estilos visuais diferentes com base no tipo da transação (ex: badge verde para receitas e badge vermelho para despesas).

3. Requisitos Não Funcionais (RNF)

Como o sistema deve fazer (as premissas técnicas, restrições de arquitetura, segurança e performance).

  • RNF01 - Paradigma de Desenvolvimento: O motor interno do sistema deve ser construído utilizando estritamente a Programação Orientada a Objetos (POO). Entidades de dados e comportamentos devem estar contidos em suas respectivas classes.
  • RNF02 - Encapsulamento de Estado: Atributos críticos (como o valor do saldo e o array do histórico) devem ser protegidos com visibilidade private, impedindo alterações diretas de scripts externos sem passar por métodos validadores.
  • RNF03 - Integridade de Tipos (PHP 8.1+): O código deve utilizar tipagem estrita de dados ativada via declare(strict_types=1); no topo de todos os arquivos de lógica para evitar comportamentos inesperados do interpretador (Type Juggling).
  • RNF04 - Tratamento Robusto de Erros: Tentativas de quebra de regras de negócio (como tentar gastar mais do que o saldo possui) devem disparar exceções (Exception), que precisam ser capturadas por blocos try/catch para exibir mensagens amigáveis na tela ao invés de travar a aplicação.
  • RNF05 - Proteção contra Reenvio de Dados (UX/HTTP): O script de processamento do formulário deve implementar o padrão PRG (Post-Redirect-Get), redirecionando o usuário de volta para a página principal após o cadastro bem-sucedido para evitar lançamentos duplicados ao atualizar a página (F5).
  • RNF06 - Interface Responsiva: A camada de visualização deve utilizar o framework Bootstrap 5 para garantir que o gerenciador financeiro funcione e seja legível tanto em navegadores de desktop quanto em dispositivos móveis.
