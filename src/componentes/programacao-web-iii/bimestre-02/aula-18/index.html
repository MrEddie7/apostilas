1. Visão Geral do Produto (Overview)

1.1 Contextualização do Problema de Negócio

No mercado de eventos e tecnologia, o maior desafio de uma plataforma em estágio inicial não é a quantidade de recursos, mas a confiabilidade da sua operação core: garantir que um usuário se inscreva em um evento, que sua vaga esteja de fato reservada e que seu ingresso seja autêntico. Falhas na validação de dados e segurança de acesso destroem a reputação de um sistema logo no lançamento, gerando superlotação e vazamento de dados gerenciais.

O Passaporte.io nasce para resolver essa dor central através de uma arquitetura enxuta, focada na estabilidade transacional entre organizadores e participantes.

1.2 A Solução: MVP Passaporte.io

Para validar o produto rapidamente no mercado, a plataforma operará em uma versão de Mínimo Produto Viável (MVP), priorizando o fluxo crítico de valor em uma interface limpa e de alta performance. O sistema consistirá em:

  • Portal Público de Descoberta: Uma vitrine otimizada para navegação e escolha de eventos por categoria.
  • Mecanismo de Inscrição Segura: O motor transacional que vincula o participante ao evento, gerando um passaporte digital criptográfico instantaneamente.
  • Backoffice do Organizador: Um painel focado exclusivamente no controle do inventário de eventos e integridade dos dados cadastrados.

1.3 Objetivos Técnicos e Engenharia de Software

Como este software possui um ciclo de desenvolvimento ágil e focado em entrega rápida, o sucesso da implementação não será medido pelo volume de telas, mas pela qualidade e robustez da engenharia aplicada no núcleo da aplicação:

  • Consistência e Integridade de Dados: O banco de dados relacional deve ser autossuficiente. As regras de integridade referencial nas tabelas e chaves estrangeiras devem impedir registros duplicados ou inconsistências na persistência de dados concorrentes na camada intermediária.
  • Segurança e Isolamento de Recursos: Implementar barreiras de software que garantam o isolamento completo dos dados no nível da requisição. Usuários mal-intencionados não devem conseguir manipular parâmetros HTTP para interceptar, ler ou alterar registros de propriedade de terceiros.
  • Otimização de Infraestrutura (Performance): Projetar as consultas ao banco de dados para suportar escalabilidade desde o primeiro dia. O sistema deve mitigar nativamente gargalos de processamento, impedindo que loops de renderização gerem conexões repetitivas e desnecessárias ao banco de dados nas listagens públicas.

1.4 Arquitetura Incremental e Fundações

Este projeto foi desenhado sob o princípio do desenvolvimento evolucionário. Esta fase foca estritamente em Persistência Relacional Avançada, Segurança de Perfil e Validação de Negócio. A precisão técnica nesta entrega é um pré-requisito crítico, pois este núcleo estável e bem-feito funcionará como a fundação obrigatória para as futuras expansões do produto, que englobarão automação de serviços, processamento de arquivos e integrações externas.

2. Perfis de Usuário & Regras de Acesso (Personas & ACL)

Para garantir o isolamento de recursos e a segurança das informações no ecossistema Passaporte.io, o sistema deve mapear e gerenciar três estados de perfis de acesso distintos. O comportamento de toda a aplicação será ditado por esta matriz de permissões.

2.1 Definição das Personas

  • Visitante (Guest / Anônimo): Qualquer usuário que acessa a plataforma sem estar autenticado no sistema. Seu escopo de navegação é estritamente de leitura e descoberta.
  • Participante (User / Client): Usuário autenticado cujo objetivo principal é consumir o catálogo de eventos e garantir sua presença neles. Não possui privilégios para criar conteúdos ou visualizar métricas internas de outros organizadores.
  • Organizador (Admin / Staff): Usuário autenticado responsável pelo fornecimento e gestão dos eventos na plataforma. Possui privilégios de escrita e gerenciamento sobre suas próprias publicações, mas atua como um usuário comum (leitura) em eventos de terceiros.

2.2 Matriz de Controle de Acesso (Access Control List - ACL)

As permissões do sistema devem seguir rigorosamente a tabela de direitos operacionais abaixo:

2.3 Regras de Proteção de Camada (Diretrizes de Implementação)

O desenvolvedor deve estruturar a aplicação de forma que os seguintes comportamentos de segurança sejam validados no nível da requisição HTTP:

2.3.1 Barreira de Autenticação Global (Garantia de Login)

Qualquer tentativa de acesso a rotas que comecem com prefixos administrativos ou acionem intenções de transação (como o ato de se inscrever) deve interceptar a requisição e redirecionar o usuário imediatamente para a tela de login, caso ele esteja anônimo.

2.3.2 Bloqueio Transversal de Perfil (Isolamento de Funcionalidade)

O sistema deve validar as propriedades do usuário logado antes de entregar o recurso.

  • Se um usuário com perfil de Participante tentar forçar a entrada digitando uma URL destinada a criadores de conteúdo, a aplicação deve abortar a execução imediatamente.
  • Se um usuário com perfil de Organizador tentar se inscrever em um evento, o sistema deve impedir a ação, garantindo que contas corporativas/gestoras não poluam a listagem de ingressos de participantes.

2.3.3 Proteção de Propriedade Regressiva (Isolamento de Registro)

Estar autenticado como Organizador não concede direito irrestrito ao banco de dados. O sistema deve validar dinamicamente se o ID do organizador logado coincide com o ID do criador do evento que está sendo manipulado. Se um organizador tentar acessar o formulário de edição ou disparar uma requisição de exclusão contra o ID de um evento que pertence a outro usuário, o sistema deve bloquear a operação na hora.

3. Requisitos Funcionais (RF)

Os Requisitos Funcionais descrevem as ações, recursos e comportamentos que o Passaporte.io deve executar para entregar valor aos usuários. Para este MVP de desenvolvimento ágil, as funcionalidades foram agrupadas em quatro módulos centrais de entrega.

3.1 Módulo 1: Autenticação e Gestão de Contas (Auth)

  • RF01 – Registro de Novos Usuários: O sistema deve fornecer uma interface para que visitantes se cadastrem informando Nome, E-mail, Senha e a escolha do Perfil de Acesso (Participante ou Organizador).
  • RF02 – Autenticação de Identidade (Login): O sistema deve validar as credenciais (E-mail e Senha) dos usuários cadastrados para liberar o acesso às áreas restritas.
  • RF03 – Encerramento de Sessão (Logout): O sistema deve permitir que o usuário desconecte sua conta com segurança, destruindo a sessão ativa no servidor.

3.2 Módulo 2: Backoffice do Organizador (Gestão de Inventário)

  • RF04 – Listagem de Eventos do Organizador: O painel administrativo do organizador deve exibir uma tabela contendo apenas os eventos criados por ele, ordenados do mais recente para o mais antigo.
  • RF05 – Criação de Evento: O organizador deve dispor de um formulário para cadastrar um evento informando: Título, Descrição, Data/Hora, Localização, Vagas Disponíveis, Categoria e o Upload do Banner de Capa.
  • RF06 – Edição de Evento: O sistema deve permitir que o organizador altere qualquer informação de um evento existente, carregando os dados atuais nos campos do formulário para modificação.
  • RF07 – Exclusão de Evento: O organizador deve ter a opção de remover um evento de sua propriedade do sistema. O sistema deve exigir uma confirmação antes de efetivar a exclusão.

3.3 Módulo 3: Motor de Inscrições (Core Transacional)

  • RF08 – Registro de Presença (Inscrição): Na tela de detalhes do evento, o sistema deve disponibilizar um botão para que o participante autenticado solicite sua inscrição na lista de presença.
  • RF09 – Geração do Passaporte Digital (Ingresso): No momento exato da confirmação da inscrição, o sistema deve gerar automaticamente um código identificador único alfanumérico para servir como o "ingresso" daquele participante para aquele evento.
  • RF10 – Histórico de Inscrições do Participante: O participante deve ter acesso a uma área restrita que liste todos os eventos nos quais ele se inscreveu, exibindo o título do evento, a data e o código do seu respectivo ingresso.
  • RF11 – Cancelamento de Inscrição: O participante deve poder abrir mão de sua vaga em um evento previamente inscrito, removendo seu nome da lista e invalidando o ingresso gerado.

3.4 Módulo 4: Portal Público de Descoberta (Vitrine)

  • RF12 – Vitrine de Eventos (Home): A página inicial e pública do sistema deve exibir cards visuais de todos os eventos ativos cadastrados na plataforma.
  • RF13 – Filtragem por Categoria: A vitrine deve disponibilizar um menu de navegação que permita ao visitante filtrar e visualizar apenas os eventos pertencientes a uma categoria selecionada (ex: clicar em "Tecnologia" e ocultar eventos de "Música").
  • RF14 – Tela de Detalhes do Evento: Ao clicar em um card na vitrine, qualquer visitante pode acessar uma página exclusiva do evento para ler a descrição completa, ver o banner ampliado, checar o local, a data, o nome do organizador responsável e o total de vagas disponíveis.

4. Regras de Negócio Obrigatórias (RN)

As Regras de Negócio determinam as condições, restrições e políticas operacionais que o software deve fazer cumprir. Qualquer tentativa de violar estas regras deve ser interceptada pelo sistema, impedindo a persistência dos dados e retornando um feedback claro ao usuário.

4.1 Restrições do Módulo de Eventos

  • RN01 – Validação de Cronograma: Um evento não pode ser cadastrado ou editado com uma data e hora retroativas. A data do evento deve ser, obrigatoriamente, posterior à data e hora atual do servidor no momento da submissão.
  • RN02 – Formato e Limite de Mídia: O banner de capa do evento deve ser obrigatoriamente um arquivo de imagem válido. O sistema deve rejeitar qualquer formato que não seja de imagem ou que ultrapasse o tamanho limite de 2 megabytes (2MB).
  • RN03 – Exclusão com Salvaguarda de Inscrições: Um organizador não pode excluir um evento que já possua participantes inscritos. Caso o evento já tenha gerado ingressos, o sistema deve bloquear a exclusão e instruir o organizador a entrar em contato com o suporte ou cancelar as inscrições previamente.

4.2 Restrições do Módulo de Inscrições e Ingressos

  • RN04 – Unicidade de Inscrição: Um participante está terminantemente proibido de se inscrever mais de uma vez no mesmo evento. O vínculo entre o usuário e o evento na tabela intermediária deve ser único.
  • RN05 – Limite Absoluto de Capacidade (Lotação): O sistema deve monitorar o número de vagas disponíveis em tempo real. Se o total de participantes inscritos atingir a capacidade máxima configurada para o evento, o botão de inscrição deve ser desativado na interface, e qualquer tentativa de requisição direta de inscrição deve ser rejeitada com um aviso de "Vagas Esgotadas".
  • RN06 – Impedimento de Auto-Inscrição: Um usuário com o perfil de Organizador não pode se inscrever em eventos (sejam eles de sua propriedade ou de terceiros). O fluxo de inscrição é exclusivo para o perfil de Participante.

4.3 Restrições de Segurança e Propriedade de Dados

  • RN07 – Integridade de Vínculo na Escrita: No momento do cadastro de um evento, o sistema deve vincular automaticamente o registro ao ID do usuário autenticado que está enviando o formulário. O sistema não deve aceitar ou confiar em IDs enviados por campos ocultos manipuláveis no HTML para definir o proprietário do evento.
  • RN08 – Imutabilidade de E-mail: O endereço de e-mail fornecido no momento do cadastro do usuário deve ser único em todo o sistema. Durante a edição de qualquer perfil ou dado, o sistema deve validar se o e-mail não colide com o de outro usuário já existente, impedindo a duplicidade.
  • RN09 – Bloqueio de Edição Transversal: Um organizador está proibido de acessar os formulários de edição, atualizar dados ou disparar comandos de exclusão contra eventos criados por outros organizadores. O ID do autor do evento deve coincidir estritamente com o ID do usuário logado para liberar qualquer operação de escrita.

5. Requisitos Não-Funcionais (RNF)

Os Requisitos Não-Funcionais definem os critérios técnicos, padrões de arquitetura, restrições de infraestrutura e parâmetros de qualidade que o Passaporte.io deve obedecer. Eles determinam como o sistema deve executar suas funções, garantindo a robustez, a segurança e a escalabilidade da aplicação.

5.1 Persistência e Modelagem de Banco de Dados (Database Architecture)

  • RNF01 – Integridade Referencial Estrita: O banco de dados relacional deve impor restrições de chaves estrangeiras (foreign keys) em todas as associações. Se uma categoria for removida, o sistema deve impedir a exclusão caso existam eventos vinculados a ela, blindando o banco contra dados órfãos.
  • RNF02 – Relação Muitos-para-Muitos Automatizada: O vínculo de inscrições deve ser gerenciado por uma tabela intermediária (pivô) formalizada. A persistência dessa relação deve atualizar de forma nativa e simultânea os campos de controle de data (timestamps) da tabela intermediária.
  • RNF03 – Criptografia de Credenciais: Nenhuma senha de usuário pode ser armazenada em texto limpo no banco de dados. O sistema deve aplicar algoritmos de hash criptográfico seguros de forma nativa antes de persistir o dado.

5.2 Performance, Escalabilidade e Consumo de Recursos

  • RNF04 – Mitigação Antigargalo (Problema N+1): É expressamente proibido realizar consultas repetitivas ao banco de dados dentro de laços de repetição (loops) na renderização de listagens. A listagem da vitrine pública deve carregar de forma ansiosa (Eager Loading) os relacionamentos de categoria e organizador. O sistema deve renderizar a página principal executando o número mínimo fixo de consultas, independentemente do volume de eventos exibidos.
  • RNF05 – Paginação de Dados: O painel do organizador e o histórico do participante não devem carregar registros de forma ilimitada em uma única requisição. O sistema deve segmentar os resultados em lotes gerenciáveis por meio de paginação nativa na camada do banco de dados.

5.3 Segurança de Aplicação e Isolamento de Requisições

  • RNF06 – Proteção Contra Injeção e Ataques Estruturais: Todos os dados recebidos via requisições HTTP devem ser sanitizados e tratados através de camadas de abstração segura (como Prepared Statements ou Query Binding), impedindo ataques de SQL Injection de forma nativa.
  • RNF07 – Proteção Contra Falsificação de Requisições: O sistema deve exigir tokens de validação dinâmicos em todas as requisições que utilizem métodos de escrita (como POST, PUT ou DELETE), mitigando riscos de ataques do tipo CSRF (Cross-Site Request Forgery).

5.4 Sistema de Arquivos e Armazenamento (Storage)

  • RNF08 – Isolamento de Arquivos Estáticos: Os uploads de banners enviados pelos organizadores devem ser armazenados em um diretório isolado e protegido do sistema de arquivos do servidor. O acesso público a essas mídias na interface web deve ser feito por meio de mapeamento de links simbólicos seguros, impedindo o acesso direto à raiz da aplicação.
  • RNF09 – Ofuscação de Nomes de Arquivos: Ao salvar uma imagem de banner no servidor, o sistema deve renomear o arquivo utilizando hashes ou identificadores únicos aleatórios. Isso evita a colisão de nomes (dois arquivos com o mesmo nome se sobrescreverem) e impede que usuários adivinhem a estrutura de arquivos do servidor.

5.5 Interface, Usabilidade e Tratamento de Erros (UX/UI)

  • RNF10 – Padronização de Feedback (Sessão Flash): O sistema deve utilizar a persistência em sessão de curto ciclo (mensagens flash) para enviar respostas de sucesso ou erro à interface. A interface visual, construída com DaisyUI, deve renderizar esses estados usando alertas semânticos (alert-success para operações concluídas e alert-error para falhas ou bloqueios).
  • RNF11 – Preservação de Estado em Falhas: Caso uma validação de formulário falhe, o sistema deve reter temporariamente os dados válidos digitados pelo usuário na sessão, repovoando os campos automaticamente ao recarregar a página. Isso evita que o usuário precise preencher todo o formulário novamente.

6. Critérios de Aceite & Formato de Entrega

Para que o projeto Passaporte.io seja considerado concluído e aceito para avaliação, ele deve passar com sucesso por todos os critérios de validação operacional e ser entregue seguindo os padrões profissionais de governança de código descritos abaixo.

6.1 Critérios de Aceite (Definição de Pronto / DoD)

O projeto só receberá parecer favorável se atender integralmente às seguintes verificações práticas:

  • CA01 – Fluxo de Cadastro e Isolamento de Telas: O visitante deve conseguir se cadastrar escolhendo seu perfil. Se logar como Participante, as rotas /admin/* devem retornar erro de acesso imediatamente. Se logar como Organizador, a rota de inscrição deve ser bloqueada.
  • CA02 – Validação Transacional de Eventos: O formulário de eventos deve rejeitar com sucesso títulos curtos, imagens acima de 2MB e, principalmente, datas retroativas, exibindo os alertas de erro em português logo abaixo de cada campo respectivo.
  • CA03 – Persistência Segura com Upload: Ao salvar um evento, a imagem correspondente deve aparecer renderizada no card da vitrine pública. O banco de dados deve registrar o caminho ofuscado do arquivo e vincular o evento ao ID do organizador sem o uso de inputs ocultos manipuláveis pelo usuário no formulário de criação.
  • CA04 – Validação do Motor de Inscrição (Tabela Pivô): Ao clicar em "Inscrever-se", o sistema deve reduzir logicamente o total de vagas ou validar a capacidade. O banco de dados deve gerar uma nova linha na tabela intermediária contendo as duas chaves estrangeiras corretas, além do ticket_code alfanumérico aleatório e o timestamp da operação.
  • CA05 – Comprovação de Mitigação N+1: O código da página inicial não deve conter consultas repetitivas dentro de loops. A listagem deve resolver o carregamento do organizador e da categoria usando carregamento ansioso.

6.2 Formato de Entrega Obrigatório

O projeto simulará o hand-off de código de uma equipe de desenvolvimento para o time de operações ou engenharia de QA. Os seguintes artefatos devem ser fornecidos:

6.2.1 Repositório no GitHub

  • O código-fonte completo deve ser disponibilizado em um repositório na nuvem (público ou privado com acesso liberado para o professor).
  • Histórico de Commits Semântico: O repositório deve demonstrar a evolução do desenvolvimento por meio de commits claros e organizados (ex: feat: implementa autenticação de perfis, fix: corrige validacao de data retroativa), evitando envios massivos com mensagens genéricas (ex: "projeto pronto" ou "ajustes").

6.2.2 Automação de Banco de Dados (Ambiente Pronto)

  • O projeto não deve depender de dumps de arquivos .sql manuais. O repositório deve conter todas as Migrations necessárias para estruturar o banco de dados do zero.
  • Seeders Obrigatórios: Deve ser fornecido um arquivo de Seeder para popular a tabela de categorias (ex: "Tecnologia", "Música", "Negócios") de forma automatizada, permitindo que o avaliador teste o sistema imediatamente após subir o ambiente.

6.2.3 Documentação de Engenharia (O Arquivo README.md)

A raiz do projeto deve conter um arquivo markdown detalhando exatamente como colocar o software em execução. O documento deve cobrir:

  • Requisitos de Ambiente: Versão utilizada do ecossistema e qual banco de dados foi configurado.
  • Passo a Passo de Inicialização: Comandos necessários para instalar as dependências, gerar a chave de segurança da aplicação e criar o link simbólico do sistema de arquivos (storage).
  • Instruções de Migração: Comando exato para rodar as migrations junto com os seeders de teste.
  • Credenciais de Teste Padrão: O documento deve listar um e-mail e senha criados previamente (via Seeder ou instrução de cadastro) para uma conta de Organizador e outra de Participante, permitindo a validação imediata das matrizes de acesso (ACL) sem a necessidade de criar novas contas do zero durante a correção.
