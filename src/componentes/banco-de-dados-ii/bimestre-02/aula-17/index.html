Teoria & Conceitos

1. O que é uma Visão (View)?

Uma visão (View) é uma tabela virtual baseada no conjunto de resultados de uma consulta SQL. Diferente das tabelas base, uma visão não possui existência física própria nem armazena dados em disco (exceto em casos específicos de visões materializadas); ela é uma "janela" ou "fotocópia" lógica que exibe dados de uma ou mais tabelas subjacentes no momento em que é consultada.

Principais Características:

  • Abstração: Oculta a complexidade de junções (JOINs) e cálculos pesados.
  • Volatilidade: O resultado da visão é recomputado sempre que ela é acessada, refletindo instantaneamente mudanças nas tabelas base.
  • Interoperabilidade: Pode ser tratada pela aplicação como se fosse uma tabela comum (SELECT, INSERT, UPDATE, DELETE).

2. Finalidades: Por que utilizar Views?

  • A. Segurança e Restrição de Acesso: As visões são ferramentas poderosas para implementar segurança no nível de coluna e linha. Você pode criar uma visão que oculte colunas sensíveis (como salários ou senhas) e conceder permissão ao usuário apenas para a visão, e não para a tabela original.
  • B. Simplificação de Consultas: Evita que o desenvolvedor tenha que reescrever expressões matemáticas ou filtros complexos repetidamente.

3. Manipulação de Dados (DML) através de Views

É possível realizar operações de INSERT, UPDATE e DELETE através de uma visão, mas existem restrições importantes:

  • Simplicidade: A visão geralmente deve ser baseada em uma única tabela para ser atualizável nativamente.
  • Chaves: Deve incluir a chave primária da tabela base se for realizar inserções.
  • Cálculos: Colunas que resultam de funções (SUM, AVG) ou cálculos não podem ser alvos de UPDATE.

Diferença Técnica:

  • MySQL: Permite atualizações automáticas em visões simples que mapeiam diretamente para uma tabela base.
  • PostgreSQL: Tradicionalmente exige a criação de Rules (regras) ou INSTEAD OF Triggers para tornar visões complexas (com JOINs) atualizáveis.

4. Segurança com GRANT e REVOKE

Para garantir que a visão cumpra seu papel de segurança, o administrador do banco de dados (DBA) deve gerenciar os privilégios com precisão, aplicando o princípio do menor privilégio. 

-- MySQL e PostgreSQL (Sintaxe ANSI)
-- 1. Garante privilégio de leitura na visão para todos os usuários
GRANT SELECT ON resumo_emails TO PUBLIC;

-- 2. Retira privilégio de deletar dados através da visão
REVOKE DELETE ON resumo_emails FROM usuario_limitado;

5. Resumo de Diferenças e Comandos

Recurso MySQL PostgreSQL
Atualização automática Sim (em visões simples). Limitada (prefere Triggers).
Views Materializadas Não nativo (exige simulação). Sim (CREATE MATERIALIZED VIEW).
Eliminação DROP VIEW nome;
Check Option WITH CHECK OPTION (garante que dados inseridos apareçam na visão). WITH CHECK OPTION (suporte completo).

Exemplo de Código

Abaixo, apresentamos exemplos práticos comparando as sintaxes entre os dois ambientes.

Sintaxe Básica (ANSI SQL)

CREATE VIEW nome_da_view AS
SELECT colunas FROM tabelas WHERE condicao;

Exemplo no MySQL

O MySQL utiliza as views para simplificar cálculos e formatação de datas.

-- Criando uma visão para resumo de envios de e-mail
CREATE VIEW vw_resumo_emails AS
SELECT 
    DATE_FORMAT(data_envio, '%d/%m/%Y') AS data_formatada,
    CONCAT(usuario, '@', host) AS remetente,
    tamanho_kb
FROM logs_email;

-- Consultando a visão como se fosse uma tabela
SELECT * FROM vw_resumo_emails WHERE tamanho_kb > 1000;

Exemplo no PostgreSQL

O PostgreSQL é frequentemente usado para encapsular junções entre múltiplas tabelas.

-- Criando uma visão que une dados de fatos com descrições (Lookup)
CREATE OR REPLACE VIEW vw_vendas_detalhadas AS
SELECT 
    p.nome_produto,
    c.categoria,
    f.quantidade,
    f.data_venda
FROM fatos_vendas f
INNER JOIN produtos p ON f.id_produto = p.id_produto
INNER JOIN categorias c ON p.id_categoria = c.id_categoria;

-- Uso da visão
SELECT nome_produto, quantidade FROM vw_vendas_detalhadas;

Dicas & Lembretes

  • Dica de Performance: Evite utilizar SELECT * dentro de definições de visões para não sobrecarregar o processamento com colunas desnecessárias das tabelas base. Use visões para expor apenas o que é estritamente necessário para o processo de negócio.
  • Ocultando Complexidade: Utilize as Views para criar uma camada de API lógica sobre seu banco de dados. Isso protege as aplicações cliente de mudanças estruturais nas tabelas base (refatoração).
  • Diferença de Persistência: Lembre-se de que Views normais são resolvidas em tempo de execução. Se precisar de alta performance em agregações complexas no PostgreSQL, estude as Materialized Views, que salvam o resultado físico no disco.
