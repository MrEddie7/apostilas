Teoria & Conceitos

1. Definição e Propriedade de Fechamento

Uma subquery é um comando SELECT aninhado dentro de outra instrução SQL (como outro SELECT, INSERT, UPDATE ou DELETE). Essa capacidade deriva da propriedade de fechamento da álgebra relacional: como o resultado de qualquer operação relacional é sempre uma nova relação (tabela), podemos usar uma expressão de tabela em qualquer lugar onde o nome de uma tabela física seria aceito.

2. Subqueries na Cláusula WHERE

Este é o uso mais comum, servindo para filtrar resultados com base em um conjunto de dados dinâmico.

A. Operador IN e NOT IN

O operador IN verifica se um valor pertence ao conjunto retornado pela subconsulta.

Exemplo: Listar produtos que participam de qualquer pedido com quantidade igual a 10. 

SELECT descricao_produto 
FROM produto 
WHERE codigo_produto IN (
    SELECT codigo_produto 
    FROM item_de_pedido 
    WHERE quantidade = 10
);

O NOT IN identifica o que não está presente no conjunto, sendo útil para encontrar "buracos" ou registros sem correspondência.

B. Operador EXISTS e NOT EXISTS

Diferente do IN, o EXISTS não retorna valores, mas um valor booleano (verdadeiro/falso) se a subconsulta retornar ao menos uma linha. Ele é frequentemente mais performático para checar a existência de relacionamentos.

Exemplo: Listar clientes que possuem ao menos um pedido cadastrado.

SELECT nome_cliente 
FROM cliente C 
WHERE EXISTS (
    SELECT 1 
    FROM pedido P 
    WHERE P.codigo_cliente = C.codigo_cliente
);

3. Subqueries na Cláusula FROM (Tabelas Derivadas)

Também chamadas de Inline Views, essas subqueries permitem tratar o resultado de um SELECT como se fosse uma tabela física, o que é ideal para realizar agregações antes de uma junção.

Exemplo: Comparar o preço de pinturas com o valor máximo por artista.

SELECT A.name, P.title, P.price
FROM artist AS A 
INNER JOIN painting AS P ON A.a_id = P.a_id
INNER JOIN (
    SELECT a_id, MAX(price) AS max_price 
    FROM painting 
    GROUP BY a_id
) AS tmp ON P.a_id = tmp.a_id AND P.price = tmp.max_price;

4. Subqueries Correlacionadas vs. Independentes

A. Subqueries Independentes (Não-Correlacionadas)

Uma subquery é classificada como independente quando ela é totalmente autônoma, ou seja, ela não faz nenhuma referência aos campos da consulta externa principal. O algoritmo de execução do SGBD resolve a consulta interna uma única vez, armazena o resultado estático na memória temporária e o entrega para a consulta externa processar o restante do filtro.

Exemplo Prático

Imagine que a diretoria da plataforma precisa listar todas as transmissões que duraram mais tempo do que a média de minutos geral de todas as lives já realizadas no sistema. 

SELECT id, titulo_live, duracao_minutos
FROM lives
WHERE duracao_minutos > (
    -- Subquery Independente: O MySQL executa esta linha uma única vez
    SELECT AVG(duracao_minutos) 
    FROM lives
);

Como o MySQL executa isso nos bastidores?

Mecânica de Execução da Subquery Independente

O algoritmo de execução do SGBD para a consulta independente segue uma esteira linear e otimizada. Os passos ocorrem na seguinte sequência de eventos:

  • Passo 1: O banco de dados isola completamente a consulta interna: SELECT AVG(duracao_minutos) FROM lives;.
  • Passo 2: O motor do banco calcula a média global de todas as linhas da tabela (vamos supor que o resultado seja 218).
  • Passo 3: O MySQL substitui todo o bloco de código da subquery por esse valor estático numérico guardado em cache.
  • Passo 4: A consulta externa principal é reescrita internamente pelo otimizador do SGBD da seguinte forma: SELECT id, titulo_live, duracao_minutos FROM lives WHERE duracao_minutos > 218;.
  • Passo 5: O banco realiza uma única varredura linear na tabela para trazer os registros que passaram no filtro, tornando o processo extremamente rápido e leve.

B. Subqueries Correlacionadas

Uma subquery é considerada correlacionada quando existe um vínculo de dependência direta entre a consulta interna e a tabela da consulta externa. A subquery interna faz referência explícita a uma ou mais colunas da query principal. Por causa dessa dependência, o SGBD é incapaz de resolver a consulta de dentro de forma isolada.

Exemplo Prático

Agora, a necessidade de negócio mudou: a diretoria precisa listar as lives que duraram mais tempo do que a média de minutos específica do jogo daquela transmissão (comparando lives de FPS apenas com a média de FPS, e RPG apenas com a média de RPG). 

SELECT l_externa.id, l_externa.titulo_live, l_externa.duracao_minutos, l_externa.id_jogo
FROM lives l_externa
WHERE l_externa.duracao_minutos > (
    -- Subquery Correlacionada: Dependência direta do apelido "l_externa"
    SELECT AVG(l_interna.duracao_minutos)
    FROM lives l_interna
    WHERE l_interna.id_jogo = l_externa.id_jogo
);

Como o MySQL executa isso nos bastidores?

Mecânica de Execução da Subquery Correlacionada (O Loop)

Ao contrário da estrutura anterior, a consulta correlacionada força o motor do MySQL a trabalhar através de um laço de repetição (loop) aninhado linha a linha. Se a tabela principal possuir 1.000 registros, a subquery rodará exatamente 1.000 vezes:

  • Passo 1: O banco de dados lê a Linha 1 da tabela da consulta externa (uma transmissão de Counter-Strike 2, onde o id_jogo = 2).
  • Passo 2: O valor 2 é injetado fisicamente dentro da subquery interna. O comando interno é executado para calcular a duração média apenas dos vídeos pertencentes ao jogo de ID 2. Se a duração da Linha 1 for maior que essa média específica de CS2, a linha é separada para o resultado.
  • Passo 3: O banco avança para a Linha 2 da tabela externa (uma transmissão de Minecraft, onde o id_jogo = 4).
  • Passo 4: O motor do SGBD reinicia a subquery interna do zero, injetando agora o valor 4 para recalcular a média de minutos consumidos apenas nos vídeos de Minecraft.
  • Passo 5: Esse ciclo repetitivo de "ler fora, injetar e recalcular dentro" se repete exaustivamente até que a última linha da tabela externa seja processada.

C. Quadro Comparativo de Performance

A diferença de comportamento do SGBD em arquiteturas de dados de grande porte, analise o resumo operacional de cada estrutura:

Critério Subquery Independente Subquery Correlacionada
Dependência Autônoma (Não usa campos de fora). Dependente (Usa apelidos da tabela externa).
Execuções Apenas 1 vez antes da query principal. N vezes (Uma vez para cada linha encontrada).
Performance Geralmente rápida e leve. Pode virar um gargalo pesado se a tabela for gigante e não tiver índices.
Analogia Olhar a previsão do tempo na TV uma vez antes de sair de casa. Olhar pela janela a cada minuto para ver se o tempo mudou antes de dar cada passo.

5. Otimização e Performance

O uso indiscriminado de subqueries pode degradar o tempo de resposta do banco de dados.

  • Evite Subqueries no SELECT: Um erro comum é colocar subqueries na lista de campos do SELECT para buscar descrições individuais, o que força o banco a executar milhares de mini-consultas. Prefira usar JOIN sempre que possível.
  • Restrições Precoces: Filtrar os dados (WHERE) dentro da subquery antes de passá-los para a consulta externa é uma técnica de otimização que reduz a massa de dados processada.
  • Indexação: Chaves estrangeiras envolvidas em subqueries correlacionadas devem ser indexadas para que a busca interna seja instantânea.
  • Cashing: SGBDs modernos como o PostgreSQL podem aumentar a velocidade em até 10% ou mais ao colocar em buffer os resultados de subqueries repetitivas.

Resumo de Operadores de Comparação em Subqueries

Operador Função Resultado esperado da Subquery
IN Verifica inclusão em lista. Uma coluna com múltiplas linhas.
EXISTS Verifica se há algum retorno. Booleano (True/False).
ALL Compara com todos os valores. Conjunto de valores.
ANY / SOME Compara com ao menos um valor. Conjunto de valores.
Escalar Usa =, <, > etc. Uma única linha e uma única coluna.

Laboratório Prático: Progressão com o Operador EXISTS

O operador EXISTS é uma das ferramentas mais eficientes do SQL para validar a existência de relacionamentos entre tabelas. Abaixo, explore a lista de exemplos práticos comentados, progredindo do uso mais simples até arquiteturas de consultas complexas de nível avançado.

1. Nível Básico: Validação Direta de Relacionamento

O uso mais tradicional do EXISTS serve para filtrar registros da tabela principal que possuem, pelo menos, um histórico correspondente na tabela secundária, sem a necessidade de duplicar linhas na tela (comportamento comum do INNER JOIN quando há múltiplos registros filhos).

Problema de Negócio

Listar o nickname de todos os streamers que já realizaram pelo menos uma transmissão (live) na plataforma. 

SELECT s.nickname 
FROM streamers s
WHERE EXISTS (
    SELECT 1 
    FROM lives l 
    WHERE l.id_streamer = s.id
);

Explicação: O MySQL lê o primeiro streamer. Ele entra na tabela de lives e procura o ID desse streamer. Assim que ele encontra a primeira live, o EXISTS recebe o sinal de verdadeiro, interrompe a busca interna para esse streamer e exibe o seu nickname. É um processo cirúrgico e rápido.

2. Nível Intermediário: Identificação de Inatividade com NOT EXISTS

O operador NOT EXISTS inverte o teste lógico. Ele só deixa passar para o resultado final os registros da tabela principal que **não** encontrarem absolutamente nenhuma correspondência na subquery interna.

Problema de Negócio

Identificar quais streamers criaram uma conta na plataforma, mas estão inativos, ou seja, nunca abriram nenhuma transmissão (live). 

SELECT s.nickname, s.data_cadastro
FROM streamers s
WHERE NOT EXISTS (
    SELECT 1 
    FROM lives l 
    WHERE l.id_streamer = s.id
);

Explicação: Esta consulta é ideal para o setor de marketing disparar e-mails de engajamento. O NOT EXISTS varre a tabela secundária e só valida o streamer se a subquery retornar um conjunto completamente vazio.

3. Nível Avançado: Filtros Multi-Tabelas e Subqueries Correlacionadas Encadeadas

Em cenários complexos de Business Intelligence (BI), o EXISTS pode conter junções (JOIN) dentro da sua própria subquery, permitindo filtrar uma tabela com base em critérios de uma terceira ou quarta tabela oculta.

Problema de Negócio

A diretoria precisa de uma lista de streamers veteranos (com patrocínio acima de 15.000,00) que já transmitiram jogos especificamente da categoria 'FPS' para espectadores que assistiram utilizando o dispositivo 'SmartTV'. 

SELECT s.nickname, s.repatria_patrocinio
FROM streamers s
WHERE s.repatria_patrocinio > 15000.00
  AND EXISTS (
      -- Subquery avançada cruzando lives, jogos e visualizações
      SELECT 1 
      FROM lives l
      INNER JOIN jogos j ON l.id_jogo = j.id
      INNER JOIN visualizacoes_live v ON l.id = v.id_live
      WHERE l.id_streamer = s.id 
        AND j.categoria = 'FPS'
        AND v.dispositivo = 'SmartTV'
  );

Explicação: Repare como a query principal permanece limpa, sem nenhum JOIN exposto. O MySQL primeiro filtra os streamers pelo valor do patrocínio (uma operação rápida). Para os sobreviventes, ele executa a subquery correlacionada complexa, verificando a existência do combo perfeito: transmissão do streamer + jogo FPS + audiência na SmartTV.

4. Nível Elite: Duplo NOT EXISTS (O Conceito de Divisão Relacional)

Este é o ápice do uso do operador. O uso de dois operadores NOT EXISTS aninhados simula a operação de **Divisão** da Álgebra Relacional. Ele serve para responder à pergunta clássica de "Quem consumiu TODOS os elementos de uma lista?".

Problema de Negócio

Achar o usuário espectador ultra-fiel: aquele que assistiu a transmissões de **todos** os jogos cadastrados na categoria 'FPS' da nossa plataforma. 

SELECT v_externa.id_usuario_espectador
FROM visualizacoes_live v_externa
WHERE NOT EXISTS (
    -- Subquery 1: Seleciona todos os jogos de FPS existentes
    SELECT j.id 
    FROM jogos j 
    WHERE j.categoria = 'FPS'
      AND NOT EXISTS (
          -- Subquery 2: Verifica se o usuário assistiu a ESSE jogo específico
          SELECT 1 
          FROM visualizacoes_live v_interna
          INNER JOIN lives l ON v_interna.id_live = l.id
          WHERE v_interna.id_usuario_espectador = v_externa.id_usuario_espectador
            AND l.id_jogo = j.id
      )
);

Explicação: Traduzindo a lógica do duplo NOT EXISTS para o português, o banco lê o seguinte: "Selecione o espectador para o qual NÃO EXISTA nenhum jogo de FPS que ele NÃO TENHA assistido". Se não há nenhum jogo de FPS que ele deixou de assistir, significa matematicamente que ele assistiu a todos!

Dicas & Lembretes

1. Independente vs. Correlacionada (Custo de Performance)

A subquery independente calcula a média geral de minutos das lives uma única vez e entrega o resultado. A correlacionada cria um loop oculto: ela reexecuta a busca interna para cada linha da tabela externa para cruzar os IDs dos jogos, o que pode travar o servidor se a tabela crescer.

2. O Fantasma do N+1 no SELECT

Evite colocar subqueries na lista de campos do SELECT para buscar o nickname do streamer. Isso força o MySQL a abrir milhares de mini-consultas em loop. Para amarrar descrições de outras tabelas, a boa prática de mercado é usar sempre o INNER JOIN.

3. Curto-Circuito Otimizado no EXISTS

O operador EXISTS trabalha com lógica de atalho (short-circuit). Assim que ele encontra a primeira live correspondente na tabela filha, ele interrompe a busca interna e valida o registro. Por isso, usar SELECT 1, SELECT * ou SELECT NULL dentro dele consome exatamente o mesmo desempenho.

4. Sintaxe Rígida do EXISTS

O EXISTS exige obrigatoriamente o nascimento de uma subquery entre os parênteses. Ao contrário do operador IN, que aceita uma lista de valores estáticos textuais ou numéricos, o EXISTS só sabe avaliar o resultado vindo de um comando SELECT.

5. O Segredo do Espectador Fiel (Divisão Relacional)

Para resolver a lógica de divisão e encontrar o usuário que assistiu a 100% dos jogos de FPS cadastrados, utilize a estrutura de duplo NOT EXISTS. Traduzido para a lógica humana, o banco lê: "Selecione o espectador para o qual NÃO EXISTA nenhum jogo de FPS que ele NÃO TENHA assistido".
