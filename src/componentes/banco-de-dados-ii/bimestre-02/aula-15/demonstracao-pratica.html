Estrutura de Tabelas (Modelo Físico ArenaStream)

Para explorarmos o conceito de subqueries (consultas aninhadas), utilizaremos o banco de dados da plataforma ArenaStream. A arquitetura foi projetada para conectar streamers, seus jogos transmitidos e as métricas de audiência dos espectadores.

1. Diagrama de Entidade e Relacionamento

O modelo abaixo detalha a conectividade do banco. Note a tabela de associação visualizacoes_live, que gerencia a audiência combinando chaves primárias e estrangeiras:

erDiagram JOGOS { int id PK varchar nome varchar categoria } STREAMERS { int id PK varchar nickname decimal repatria_patrocinio date data_cadastro } LIVES { int id PK int id_streamer FK int id_jogo FK int duracao_minutos varchar titulo_live } VISUALIZACOES_LIVE { int id_live FK "PK, FK" int id_usuario_espectador PK int minutos_assistidos varchar dispositivo } STREAMERS ||--o{ LIVES : "transmite" JOGOS ||--o{ LIVES : "id_jogo" LIVES ||--o{ VISUALIZACOES_LIVE : "recebe_audiencia"

2. Script de Criação das Tabelas em SQL

Execute o código abaixo no seu ambiente MySQL para construir a estrutura física do laboratório prático. O script limpa resquícios de execuções anteriores para evitar conflitos de chaves estrangeiras: 

-- Limpeza de tabelas antigas para garantir um ambiente limpo
SET FOREIGN_KEY_CHECKS = 0;
DROP TABLE IF EXISTS visualizacoes_live;
DROP TABLE IF EXISTS lives;
DROP TABLE IF EXISTS streamers;
DROP TABLE IF EXISTS jogos;
SET FOREIGN_KEY_CHECKS = 1;

-- Tabela 1: Catálogo de Jogos da Plataforma
CREATE TABLE jogos (
    id INT PRIMARY KEY AUTO_INCREMENT,
    nome VARCHAR(100) NOT NULL,
    categoria VARCHAR(50) NOT NULL
);

-- Tabela 2: Cadastro de Criadores de Conteúdo (Streamers)
CREATE TABLE streamers (
    id INT PRIMARY KEY AUTO_INCREMENT,
    nickname VARCHAR(50) NOT NULL,
    repatria_patrocinio DECIMAL(10,2) NULL,
    data_cadastro DATE NOT NULL
);

-- Tabela 3: Registro de Transmissões Realizadas (Lives)
CREATE TABLE lives (
    id INT PRIMARY KEY AUTO_INCREMENT,
    id_streamer INT,
    id_jogo INT,
    duracao_minutos INT NOT NULL,
    titulo_live VARCHAR(150),
    FOREIGN KEY (id_streamer) REFERENCES streamers(id),
    FOREIGN KEY (id_jogo) REFERENCES jogos(id)
);

-- Tabela 4: Histórico de Audiência por Espectador
CREATE TABLE visualizacoes_live (
    id_live INT,
    id_usuario_espectador INT,
    minutos_assistidos INT NOT NULL,
    dispositivo VARCHAR(30),
    PRIMARY KEY (id_live, id_usuario_espectador),
    FOREIGN KEY (id_live) REFERENCES lives(id)
);

Caderno de Consultas: Do Básico ao Avançado

Abaixo está a coleção de desafios práticos para o laboratório. Cada consulta foi projetada para explorar um comportamento específico do otimizador do MySQL, demonstrando o poder das subconsultas em cenários reais de análise de dados.

1. Cenário Global: Subquery Independente no WHERE (Operador Escalar)

Utilizada quando precisamos filtrar registros com base em uma estatística que precisa ser calculada previamente na tabela inteira. A consulta interna retorna um único valor (um escalar).

Problema de Negócio

A equipe de marketing precisa listar os dados de todas as lives que tiveram uma duração estritamente maior do que a média de duração de todas as transmissões já realizadas na plataforma.

SELECT id, titulo_live, duracao_minutos
FROM lives
WHERE duracao_minutos > (
    -- Subquery Independente: Executa apenas uma vez
    SELECT AVG(duracao_minutos) 
    FROM lives
);

Mecânica de Execução nos Bastidores

O MySQL isola a subquery e calcula a média aritmética global da tabela de lives (que resulta em 232.85 minutos). Ele substitui o bloco interno por esse número, reduzindo a query principal para uma busca linear simples: WHERE duracao_minutos > 232.85. O resultado final trará as transmissões de 360, 240 e 300 minutos.

2. Cenário por Categoria: Subquery Correlacionada no WHERE

Utilizada quando o critério de filtragem não é global, mas depende de uma característica específica de cada linha que está sendo processada pela consulta externa. Cria um loop lógico.

Problema de Negócio

A diretoria precisa refinar o relatório anterior: queremos listar as lives que duraram mais tempo do que a média de minutos específica do jogo ao qual ela pertence (comparando lives de FPS com a média de FPS, e RPG com a média de RPG).

SELECT l_externa.id, l_externa.titulo_live, l_externa.duracao_minutos, l_externa.id_jogo
FROM lives l_externa
WHERE l_externa.duracao_minutos > (
    -- Subquery Correlacionada: Depende do "id_jogo" da linha de fora
    SELECT AVG(l_interna.duracao_minutos)
    FROM lives l_interna
    WHERE l_interna.id_jogo = l_externa.id_jogo
);

Mecânica de Execução nos Bastidores

O motor do MySQL lê a primeira linha de l_externa (ID 101, jogo de CS2, que é ID 2). Ele captura o valor 2, joga para dentro da subquery e calcula a média apenas das lives de CS2 (360 + 180 = 540 / 2 = 270 minutos). Como a live 101 dura 360 minutos, ela passa no teste. O banco avança para a linha 102 (também CS2), roda a subquery de novo, mas como ela dura 180 minutos (menor que 270), ela é descartada. Esse loop se repete para cada uma das 7 linhas da tabela.

3. Cenário de Relacionamento Silencioso: Operador EXISTS

O operador EXISTS avalia apenas se a subquery retorna linhas (True) ou não (False). É ideal para testar a existência de vínculos entre tabelas sem a necessidade de duplicar dados na tela, usando a lógica de curto-circuito.

Problema de Negócio

Listar o ID e o nickname de todos os streamers que possuem pelo menos uma transmissão gravada no sistema, omitindo os que nunca transmitiram.

SELECT s.id, s.nickname
FROM streamers s
WHERE EXISTS (
    -- O SELECT 1 é um padrão estritamente técnico, o banco ignora o retorno e foca na existência
    SELECT 1 
    FROM lives l 
    WHERE l.id_streamer = s.id
);

Mecânica de Execução nos Bastidores

O MySQL analisa o streamer Gaules (ID 10). Ele entra na tabela de lives procurando por id_streamer = 10. Ele acha a linha 101. No mesmo instante, o EXISTS recebe "True", encerra a busca interna para o Gaules e passa para o próximo streamer. Ele não perde tempo escaneando a tabela inteira. O streamer StreamerNovato (ID 50) não encontrará nenhuma linha, fazendo o EXISTS retornar False, ocultando-o da listagem.

4. Cenário de Auditoria e Inatividade: Operador NOT EXISTS

Inverte completamente a lógica booleana do teste anterior. Só permite a exibição do registro principal se a subquery interna retornar um conjunto completamente vazio.

Problema de Negócio

Extrair uma lista de streamers que realizaram o cadastro na plataforma, mas estão totalmente inativos (nunca abriram nenhuma live).

SELECT s.id, s.nickname, s.data_cadastro
FROM streamers s
WHERE NOT EXISTS (
    SELECT 1 
    FROM lives l 
    WHERE l.id_streamer = s.id
);

Mecânica de Execução nos Bastidores

O MySQL faz o batimento de chaves. Para os streamers 10, 20, 30 e 40, a subquery localiza registros de lives, fazendo o NOT EXISTS resultar em Falso (barrando-os). Quando chega no streamer 50 (StreamerNovato), a subquery retorna zero linhas. O NOT EXISTS transforma essa ausência em Verdadeiro, imprimindo o novato na tela.

5. Nível Elite: Divisão Relacional com Duplo NOT EXISTS

O ápice da lógica SQL. É a estrutura utilizada para responder à pergunta clássica de engenharia de dados: "Quais registros da tabela A se relacionaram com TODOS os registros específicos da tabela B?".

Problema de Negócio

Identificar o ID do usuário espectador "Ultra-Fiel": aquele que possui histórico de visualização em **todos** os jogos cadastrados na categoria 'FPS'.

SELECT DISTINCT v_externa.id_usuario_espectador
FROM visualizacoes_live v_externa
WHERE NOT EXISTS (
    -- Subquery 1: Mapeia o catálogo alvo (Todos os jogos de FPS)
    SELECT j.id 
    FROM jogos j 
    WHERE j.categoria = 'FPS'
      AND NOT EXISTS (
          -- Subquery 2: Testa o cruzamento do usuário com o jogo alvo
          SELECT 1 
          FROM visualizacoes_live v_interna
          INNER JOIN lives l ON v_interna.id_live = l.id
          WHERE v_interna.id_usuario_espectador = v_externa.id_usuario_espectador
            AND l.id_jogo = j.id
      )
);

Mecânica de Execução nos Bastidores

No nosso catálogo, existem dois jogos FPS: ID 2 (CS2) e ID 3 (Valorant). O MySQL analisa o usuário 501. A Subquery 2 descobre que ele assistiu CS2, mas nunca assistiu Valorant. O jogo ID 3 fica "sozinho" na Subquery 1, fazendo a Subquery 1 retornar uma linha. O NOT EXISTS externo vê essa linha e descarta o usuário 501. Quando o banco analisa o **usuário 500**, a Subquery 2 confirma que ele assistiu lives de CS2 (101 e 102) e também a live de Valorant (107). Portanto, não sobra nenhum jogo de FPS na Subquery 1. O conjunto interno fica vazio. O NOT EXISTS externo recebe "True" e aprova o usuário 500 como o único espectador ultra-fiel da plataforma.

Cópia e Evolução de Dados com Subqueries no INSERT

Em processos de migração de sistemas ou refatoração de bancos de dados, é muito comum precisarmos transferir o conteúdo de uma tabela antiga para uma nova estrutura reformulada. Em vez de escrever múltiplos comandos linha a linha, podemos utilizar uma subquery acoplada ao comando INSERT INTO ... SELECT para processar a carga em lote.

1. Criação da Nova Tabela (jogos2)

A nova tabela receberá os mesmos campos da estrutura original, além de uma nova coluna chamada data_inclusao, que armazenará o momento exato em que o registro foi migrado:

-- Criando a nova estrutura de destino
CREATE TABLE jogos2 (
    id INT PRIMARY KEY AUTO_INCREMENT,
    nome VARCHAR(100) NOT NULL,
    categoria VARCHAR(50) NOT NULL,
    data_inclusao DATETIME NOT NULL -- Nova coluna adicionada na arquitetura
);

2. O Comando INSERT com Subquery

Para realizar a cópia, omitimos a cláusula VALUES tradicional e injetamos uma subquery SELECT. As colunas dinâmicas da tabela antiga são mapeadas diretamente, e a nova coluna recebe uma função do sistema (NOW()) para preencher a informação faltante em tempo de execução:

-- Inserindo dados em lote através de uma consulta aninhada
INSERT INTO jogos2 (id, nome, categoria, data_inclusao)
SELECT 
    id, 
    nome, 
    categoria, 
    NOW() -- Alimenta a nova coluna com a data e hora atual do servidor
FROM jogos;

Mecânica de Execução e Boas Práticas

O motor do MySQL executa a subquery interna na tabela jogos, monta uma tabela temporária em memória com os resultados e a joga diretamente para dentro da tabela jogos2 em uma única transação atômica. Mostre aos alunos que a ordem das colunas no INSERT deve ser exatamente a mesma ordem das colunas projetadas no SELECT para que os tipos de dados não se cruzem inversamente.
