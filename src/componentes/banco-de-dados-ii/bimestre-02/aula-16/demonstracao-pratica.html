Laboratório Prático: Otimização de Performance com Índices (INDEX)

Por padrão, quando uma busca é realizada utilizando a cláusula WHERE, o SGBD precisa escanear o arquivo de dados inteiro no disco rígido, linha por linha, para encontrar as correspondências. Esse comportamento é conhecido como Full Table Scan. À medida que o banco de dados cresce, essa operação se torna lenta e consome muita memória do servidor. Para solucionar esse gargalo, criamos Índices, que funcionam como o índice remissivo de um livro técnico, apontando diretamente para o endereço físico do registro no disco através de uma estrutura de árvore equilibrada (B+Tree).

1. Estrutura das Tabelas (Banco TechForge)

Criação das tabelas para o experimento, englobando o cadastro de clientes e o histórico de movimentações de estoque de hardware:

-- Limpeza preventiva do ambiente de teste
SET FOREIGN_KEY_CHECKS = 0;
DROP TABLE IF EXISTS movimentacoes_estoque;
DROP TABLE IF EXISTS clientes_teste;
SET FOREIGN_KEY_CHECKS = 1;

-- Tabela de Clientes
CREATE TABLE clientes_teste (
    id INT PRIMARY KEY AUTO_INCREMENT,
    nome VARCHAR(100) NOT NULL,
    nivel_cadastro VARCHAR(20) NOT NULL
);

-- Tabela de Movimentação de Estoque (Alvo dos testes de carga)
CREATE TABLE movimentacoes_estoque (
    id INT PRIMARY KEY AUTO_INCREMENT,
    id_cliente INT,
    componente VARCHAR(100) NOT NULL,
    tipo_movimentacao VARCHAR(20) NOT NULL,
    quantidade INT NOT NULL,
    data_registro DATE NOT NULL,
    FOREIGN KEY (id_cliente) REFERENCES clientes_teste(id)
);

3. O Cenário Sem Índice: Analisando o Full Table Scan

Antes de aplicar qualquer otimização, uma busca por uma string exata permite auditar o comportamento do motor do banco de dados:

-- Execução da consulta com o comando EXPLAIN
EXPLAIN SELECT * FROM movimentacoes_estoque 
WHERE tipo_movimentacao = 'ENTRADA';

É preciso observar as colunas geradas pelo comando EXPLAIN. A coluna type exibirá o valor ALL (indicando que 100% das linhas físicas foram lidas no HD) e a coluna key retornará NULL, comprovando a ausência de chaves de aceleração.

4. Aplicação Prática: Exemplos Diferentes de Índices

Abaixo estão mapeadas as principais estratégias de indexação com base nos padrões de acesso do sistema de e-commerce:

Exemplo A: Índice Simples (Filtros de Categoria/Status)

Criado sobre uma única coluna que recebe buscas constantes na cláusula WHERE:

CREATE INDEX idx_mov_tipo ON movimentacoes_estoque(tipo_movimentacao);

Exemplo B: Índice Composto (Relatórios de Auditoria Cruzada)

Indicado quando a aplicação realiza buscas casadas utilizando duas ou mais colunas simultaneamente. A ordem das colunas determina o portão de entrada da árvore de busca:

CREATE INDEX idx_mov_componente_data ON movimentacoes_estoque(componente, data_registro);

5. O Cenário Com Índice: Validando a Otimização

Após a criação dos índices, a execução da consulta de diagnóstico com os mesmos critérios anteriores permite validar a mudança:

-- Auditoria da consulta após a indexação
EXPLAIN SELECT * FROM movimentacoes_estoque 
WHERE tipo_movimentacao = 'ENTRADA';

Ao rodar este comando, a coluna type mudará de ALL para ref. A coluna key mostrará o nome do índice utilizado (idx_mov_tipo) e a coluna rows indicará que o banco de dados leu apenas a fração exata de registros necessários, ignorando o restante das linhas da tabela.

6. Testando o Índice Composto e a Regra de Escopo

Para fixar o entendimento sobre índices compostos, o plano de execução de duas consultas analíticas distintas deve ser comparado:

-- Consulta 1: Utiliza o índice composto (passa pelas duas colunas indexadas)
EXPLAIN SELECT * FROM movimentacoes_estoque 
WHERE componente = 'Processador Ryzen 7' AND data_registro = '2026-01-06';

-- Consulta 2: NÃO utiliza o índice composto (Regra da Esquerda para a Direita)
EXPLAIN SELECT * FROM movimentacoes_estoque 
WHERE data_registro = '2026-01-06';

Dicas & Lembretes

  • O comando EXPLAIN é a ferramenta oficial do engenheiro de dados para validar se o plano de execução elaborado pelo otimizador do SGBD está correto antes de enviar o código para o ambiente de produção.
  • A coluna possible_keys indica quais índices criados eram elegíveis para aquela consulta e qual deles foi o escolhido final para a execução.
  • Sempre verifique a sintaxe específica do seu SGBD, pois alguns motores tratam índices implícitos de chaves estrangeiras de forma automatizada no momento da criação das tabelas.
